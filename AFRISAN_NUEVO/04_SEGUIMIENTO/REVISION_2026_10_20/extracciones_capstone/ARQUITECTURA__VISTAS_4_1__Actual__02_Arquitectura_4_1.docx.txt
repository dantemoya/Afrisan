P19: 1. Introducción
P20: Este documento presenta la arquitectura de software del Sistema de Gestión de Refrigerantes AFRISAN utilizando el modelo de Vistas 4+1 de Kruchten, correspondiente al paquete de trabajo 1.4 de la EDT del proyecto. El modelo describe la arquitectura desde cinco perspectivas complementarias: Vista Lógica, Vista de Desarrollo, Vista de Procesos, Vista Física, y una quinta vista (+1) de Escenarios que ilustra cómo las cuatro vistas anteriores trabajan juntas para soportar los casos de uso del sistema.
P21: Estas vistas son consistentes con el resto de la documentación de arquitectura del proyecto: el Diagrama Entidad-Relación (DER) y diccionario de datos, la Identificación de APIs, los Recursos Técnicos y el EDT de 3 fases, todos elaborados sobre el stack tecnológico oficial: ASP.NET Core Web API (.NET 8), Entity Framework Core 8, Blazor WebAssembly, .NET MAUI, PostgreSQL 16 en Supabase Cloud, y despliegue en Microsoft Azure App Service.

P68: 3. Vista de Desarrollo
P69: La Vista de Desarrollo describe la organización del código fuente mediante una arquitectura cliente-servidor de tres capas lógicas. Esta arquitectura separa la presentación, la lógica de negocio y la persistencia de datos, manteniendo una comunicación controlada entre Afrisan.Web, Afrisan.Api y PostgreSQL/Supabase.
P71: Figura 2. Vista de Desarrollo — tres capas lógicas y sus componentes principales.
P72: Capa lógica / componente
P73: Contenido
P74: Presentación — Afrisan.Web / cliente móvil previsto
P75: Componentes Blazor WebAssembly para la aplicación web y, en el alcance previsto, pantallas .NET MAUI para el cliente móvil. Esta capa contiene vistas, formularios, navegación y consumo de la API REST; no accede directamente a la base de datos.
P76: Lógica de negocio — Afrisan.Api
P77: Backend ASP.NET Core Web API. Contiene controladores, DTOs, validaciones, reglas de registro, despacho, retorno, consulta QR, auditoría y coordinación de operaciones mediante Entity Framework Core.
P78: Persistencia — PostgreSQL / Supabase
P79: Base de datos relacional central. Administra cilindros, gases refrigerantes, movimientos, intervenciones, auditoría, relaciones, índices, transacciones y restricciones de integridad.
P80: Integraciones y servicios previstos
P81: SQLite para persistencia local offline del cliente móvil, Azure App Service para despliegue del backend y Power BI para reportería. Estos componentes se validarán según su estado de implementación.
P82: Esta organización permite trabajar en paralelo: el frontend desarrolla vistas y formularios, la API centraliza validaciones y reglas de negocio, y PostgreSQL/Supabase conserva relaciones, restricciones e historial. Las integraciones futuras se documentan como componentes previstos o en validación.
P84: 4. Vista de Procesos
P85: La Vista de Procesos describe el comportamiento previsto del sistema en tiempo de ejecución. En la solución actual, Afrisan.Web consume de forma asíncrona las operaciones disponibles de Afrisan.Api. Para el escenario futuro de una intervención en terreno se propone incorporar un cliente .NET MAUI con almacenamiento SQLite y sincronización diferida; dichos mecanismos todavía requieren implementación y pruebas. El flujo siguiente es una representación de diseño, no una ejecución verificada.
P87: Figura 3. Vista de Procesos — flujo propuesto para registrar una intervención con y sin conexión.
P89: Se propone realizar las llamadas de los clientes a la API de manera asíncrona para evitar que la espera de red bloquee la interfaz. Este comportamiento deberá comprobarse en los clientes implementados.
P90: En el cliente móvil .NET MAUI previsto, un mecanismo de sincronización en segundo plano deberá reintentar el envío de registros almacenados localmente cuando se recupere la conectividad. Se deberán definir y probar idempotencia, resolución de conflictos y recuperación ante errores.
P91: Se prevé utilizar el procesamiento asíncrono de ASP.NET Core para atender solicitudes concurrentes; los límites de carga y la integridad de operaciones simultáneas deberán validarse mediante pruebas específicas.
P92: Para las operaciones que exijan atomicidad, la confirmación se producirá después del commit de la transacción en PostgreSQL. La autorización de usuarios deberá comprobarse en la API; una eventual política de Row-Level Security (RLS) requerirá configuración y verificación independiente en la base de datos y no se presupone aplicada por la transacción.

P140: 6.1 Escenario previsto: «Técnico registra una intervención con fuga detectada, sin conexión»
P141: Paso
P142: Vista involucrada
P143: Qué ocurre
P144: 1
P145: Lógica
P146: En el escenario previsto, el técnico completaría en .NET MAUI un formulario de intervención con tipo «fuga detectada».
P147: 2
P148: Procesos
P149: Ante la ausencia de conectividad, el cliente móvil propuesto guardaría la operación en SQLite local hasta poder sincronizarla; la persistencia y el mecanismo de reintento requieren implementación y pruebas.
P150: 3
P151: Desarrollo
P152: Al recuperar conectividad, el cliente móvil previsto enviaría la operación a Afrisan.Api mediante la API REST. El backend deberá validar los datos y aplicar las reglas de negocio.
P153: 4
P154: Lógica
P155: Las reglas de negocio previstas calcularían el balance de masa y determinarían el estado del semáforo según los umbrales que se aprueben; las fórmulas y resultados deberán comprobarse.
P156: 5
P157: Desarrollo
P158: Afrisan.Api persistiría los cambios mediante Entity Framework Core; PostgreSQL/Supabase deberá confirmarlos de forma atómica para las operaciones que lo requieran.
P159: 6
P160: Física
P161: En el despliegue futuro, se prevé alojar la API en Azure App Service y la base de datos en PostgreSQL/Supabase. El control de acceso deberá verificarse; una eventual RLS no se considera implementada.
P162: 7
P163: Física
P164: Una integración futura de Power BI podría consultar los datos autorizados para mostrar intervenciones y métricas. La frecuencia de actualización y los permisos deberán definirse y probarse.
P165: 8
P166: Procesos
P167: Se propone que el jefe de grupo consulte el estado del semáforo desde Blazor. Si se requiere actualización en tiempo real sin recarga, deberá diseñarse e implementarse un mecanismo específico.
P168: Este escenario de diseño relaciona el cálculo de negocio, su ubicación en Afrisan.Api, la sincronización móvil prevista, el despliegue futuro y la consulta de resultados. No constituye evidencia de que el cliente offline, Azure, Power BI o las alertas en tiempo real se encuentren operativos.
