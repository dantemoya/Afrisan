P152: 6. Recursos técnicos
P153: 6.1 Hardware
P154: Dispositivos móviles (Android/iOS) con cámara, para el personal técnico y de bodega — escaneo de código QR/barras y captura de fotografías de respaldo.
P155: Estaciones de trabajo para el personal administrativo (Jefe de grupo, Jefe de bodega, Administrador general).
P156: Impresora de etiquetas térmicas para la generación física de códigos QR/barras de los cilindros (opcional, a validar con AFRISAN).
P157: 6.2 Software y frameworks
P158: Frontend móvil previsto: .NET MAUI (.NET 8), con patrón MVVM aplicado únicamente a la interfaz del cliente móvil, Camera.MAUI / ZXing.Net.MAUI para cámara y lectura QR, y SQLite para funcionamiento offline.
P159: Frontend web/escritorio: Blazor WebAssembly (.NET 8), consumidor de la API REST. El diseño de despliegue contempla HTTPS/JSON; el entorno local de desarrollo puede operar con una configuración distinta y deberá verificarse antes de producción.
P160: Backend/API REST: ASP.NET Core Web API (.NET 8) con Entity Framework Core 8. Corresponde a la capa de lógica de negocio y centraliza validaciones, reglas de inventario, trazabilidad, auditoría y acceso controlado a los datos.
P161: Autenticación prevista: JSON Web Tokens (JWT) mediante ASP.NET Core Authentication, con autorización por roles y almacenamiento seguro de credenciales. Su desarrollo y verificación permanecen pendientes.
P162: 6.3 Base de datos y almacenamiento
P163: Base de datos central: PostgreSQL / Supabase.
P164: Almacenamiento local offline en dispositivos móviles: SQLite (sqlite-net-pcl), con sincronización asíncrona hacia la API.
P165: 6.4 Infraestructura y servicios cloud
P166: Hosting del backend: Microsoft Azure App Service. Base de datos central: PostgreSQL 16 alojado en Supabase Cloud.
P167: Power BI Desktop y Power BI Service, para la construcción y publicación del dashboard ejecutivo.
P168: 6.5 Herramientas de gestión y control de calidad
P169: Control de versiones: Git / GitHub, con flujo de ramas y revisión de código (pull requests).
P170: Gestión ágil del proyecto: Trello, organizado mediante Product Backlog, Sprint Backlog y seguimiento por estados.
P171: Pruebas de seguridad: OWASP ZAP y Nessus, para la mitigación de vulnerabilidades (SQLi, XSS, RLS).
P172: Documentación técnica: Google Drive para entregables y evidencias, y GitHub para código y documentación técnica.

P253: 8. Apoyo a la factibilidad técnica
P254: Esta sección entrega un análisis preliminar de factibilidad técnica del proyecto, como apoyo a la evaluación de factibilidad general del Proyecto de Título.
P255: 8.1 Factibilidad tecnológica
P256: Las tecnologías seleccionadas —.NET MAUI, Blazor WebAssembly, ASP.NET Core Web API, Entity Framework Core, PostgreSQL/Supabase, SQLite, Azure App Service y Power BI— son tecnologías maduras, documentadas y compatibles entre sí. La arquitectura global se organiza como cliente-servidor de tres capas lógicas, lo que reduce la ambigüedad entre presentación, lógica de negocio y persistencia, y facilita la integración progresiva entre componentes.
P257: 8.2 Factibilidad de infraestructura
P258: La solución propuesta no requiere infraestructura física adicional relevante por parte de AFRISAN: los dispositivos móviles y estaciones de trabajo ya existen o son de bajo costo de adquisición, y el backend/base de datos se aloja en servicios cloud gestionados, evitando la necesidad de servidores propios.
P259: 8.3 Factibilidad de integración y trabajo offline
P260: El requisito de funcionamiento offline en la app móvil (RF-05, RNF-10) es técnicamente factible mediante SQLite local y sincronización diferida con la API REST. Se identifica como punto de atención el diseño de reglas de resolución de conflictos de sincronización (ver riesgo R4 del ERS).
P261: 8.4 Factibilidad de seguridad
P262: El cumplimiento de mitigaciones OWASP (RNF-01, RNF-02) es alcanzable dentro del plazo del proyecto mediante prácticas estándar (autenticación con JWT, cifrado de contraseñas, HTTPS/TLS, validación de entradas) y la ejecución de pruebas de seguridad automatizadas (OWASP ZAP, Nessus) antes de la entrega.
P263: 8.5 Factibilidad respecto al equipo y al tiempo disponible
P264: Dado que las debilidades declaradas por el equipo incluyen metodologías ágiles, levantamiento de requerimientos y planificación de tiempos, se considera necesario reforzar estas competencias durante la fase de análisis y diseño para asegurar que el alcance definido sea abordable dentro de la dedicación estimada de 8 a 12 horas semanales por integrante durante el segundo semestre académico.
P265: 8.6 Conclusión preliminar
P266: En base a lo anterior, el proyecto se considera técnicamente factible si se mantiene el alcance definido en el ERS, se priorizan los módulos críticos de intervenciones, balance de masa/semáforo y sincronización offline, y se da seguimiento activo a los riesgos R1, R2 y R4.
