P20: 1. Introducción
P21: Este documento entrega un análisis de apoyo a la factibilidad técnica del proyecto APT AFRISAN, como insumo para la evaluación de factibilidad general del Proyecto de Título. Se evalúan las dimensiones tecnológica, de infraestructura, de integración/trabajo offline, de seguridad y de capacidad del equipo, y se comparan alternativas tecnológicas relevantes.
P22: 2. Factibilidad tecnológica
P23: Las tecnologías seleccionadas para AFRISAN —.NET MAUI (.NET 8), Blazor WebAssembly (.NET 8), ASP.NET Core Web API (.NET 8), Entity Framework Core 8, PostgreSQL 16 en Supabase, SQLite, Microsoft Azure App Service y Power BI— son tecnologías maduras, documentadas y compatibles entre sí. La concentración del desarrollo principal en el ecosistema .NET reduce la complejidad de integración y el riesgo tecnológico del proyecto.
P24: 3. Factibilidad de infraestructura
P25: La solución propuesta no requiere infraestructura física adicional relevante por parte de AFRISAN: los dispositivos móviles y estaciones de trabajo ya existen o son de bajo costo de adquisición, y el backend/base de datos se aloja en servicios cloud gestionados, evitando la necesidad de servidores propios o de personal de TI dedicado a su mantención.
P26: 4. Factibilidad de integración y trabajo offline
P27: El requisito de funcionamiento offline en la app móvil (RF-06) es técnicamente factible mediante SQLite local y un mecanismo de sincronización diferida con la API REST. Este patrón permite registrar información en terreno sin conectividad y sincronizarla cuando se recupera el acceso a Internet. Se mantiene como punto de atención el diseño de reglas de resolución de conflictos de sincronización, identificado como un riesgo técnico relevante del proyecto.
P28: 5. Factibilidad de seguridad
P29: El cumplimiento de los requisitos de seguridad (RNF-01, RNF-06 y RNF-07) es técnicamente factible dentro del plazo del proyecto mediante prácticas estándar: autenticación con JWT, hash seguro de contraseñas, comunicación mediante HTTPS/TLS, validación de entradas, control de acceso por roles y pruebas de seguridad automatizadas (OWASP ZAP, Nessus) antes de la entrega final.
P30: 6. Factibilidad respecto al equipo y al tiempo disponible
P31: Considerando las debilidades del equipo en metodologías ágiles, levantamiento de requerimientos y planificación, estas competencias deberán reforzarse durante análisis y diseño para mantener el alcance dentro de la dedicación prevista de 8 a 12 horas semanales por integrante.

P87: 9. Conclusión y recomendación
P88: En base al análisis anterior, el proyecto se considera técnicamente factible, siempre que se mantenga acotado el alcance definido en el ERS, se prioricen los módulos críticos (registro de intervenciones, cálculo de balance de masa/semáforo GEI y sincronización offline) en las primeras iteraciones, y se dé seguimiento activo a los riesgos de mayor criticidad identificados en el ERS.
P89: Las principales decisiones tecnológicas se encuentran definidas: .NET MAUI para la aplicación móvil, Blazor WebAssembly para la aplicación web, ASP.NET Core Web API y Entity Framework Core para el backend, PostgreSQL/Supabase para datos y Azure App Service para despliegue. Esto permite avanzar a la fase de desarrollo sin bloqueos por selección de plataforma.
