P19: 1. Introducción
P20: Este documento presenta la arquitectura de software del Sistema de Gestión de Refrigerantes AFRISAN utilizando el modelo de Vistas 4+1 de Kruchten, correspondiente al paquete de trabajo 1.4 de la EDT del proyecto. El modelo describe la arquitectura desde cinco perspectivas complementarias: Vista Lógica, Vista de Desarrollo, Vista de Procesos, Vista Física, y una quinta vista (+1) de Escenarios que ilustra cómo las cuatro vistas anteriores trabajan juntas para soportar los casos de uso del sistema.
P21: Estas vistas son consistentes con el resto de la documentación de arquitectura del proyecto: el Diagrama Entidad-Relación (DER) y diccionario de datos, la Identificación de APIs, los Recursos Técnicos y el EDT de 3 fases, todos elaborados sobre el stack tecnológico oficial: ASP.NET Core Web API (.NET 8), Entity Framework Core 8, Blazor WebAssembly, .NET MAUI, PostgreSQL 16 en Supabase Cloud, y despliegue en Microsoft Azure App Service.

P68: 3. Vista de Desarrollo
P69: La Vista de Desarrollo describe la organización del código fuente en capas, siguiendo el estilo de Arquitectura Limpia (Clean Architecture) con separación de responsabilidades y regla de dependencia hacia el centro (el Dominio no depende de ninguna otra capa).
P71: Figura 2. Vista de Desarrollo — organización en capas (Clean Architecture).
P72: Capa (proyecto .NET)
P73: Contenido
P74: AFRISAN.Presentation
P75: Componentes Blazor (web) y páginas/ViewModels .NET MAUI (móvil), siguiendo el patrón MVVM en el cliente móvil.
P76: AFRISAN.Application
P77: Casos de uso implementados como Commands y Queries (patrón CQS), DTOs de entrada/salida, validadores, e interfaces de repositorio que la infraestructura debe implementar.
P78: AFRISAN.Domain
P79: Entidades del dominio (Usuario, Cliente, Local, Cilindro, Intervención, MovimientoInventario, Costo, IndicadorAmbiental, Auditoría), enums, reglas de negocio y excepciones de dominio. No depende de ninguna otra capa.
P80: AFRISAN.Infrastructure
P81: Implementación de los repositorios con Entity Framework Core 8 sobre PostgreSQL/Supabase, servicios de lectura de código QR, y el conector de exportación de datos hacia Power BI.
P82: Esta organización permite que el equipo trabaje en paralelo: por ejemplo, el desarrollo de un caso de uso en AFRISAN.Application puede avanzar con una implementación simulada (mock) del repositorio, mientras otro integrante completa la implementación real en AFRISAN.Infrastructure, conforme a los Sprints definidos en la Fase 2 del EDT.
P84: 4. Vista de Procesos
P85: La Vista de Procesos describe el comportamiento del sistema en tiempo de ejecución, incluyendo la concurrencia entre la interfaz de usuario, la tarea de sincronización en segundo plano de la app móvil, y el procesamiento asíncrono de solicitudes en el backend. Se ilustra con el flujo de registro de una intervención, que es el proceso más crítico del sistema.
P87: Figura 3. Vista de Procesos — registro de una intervención, con y sin conexión.
P89: El hilo principal de la app móvil/web nunca bloquea la interfaz mientras se espera una respuesta de red; las llamadas a la API se realizan de forma asíncrona (async/await).
P90: Cuando no hay conexión, un Background Service de .NET MAUI reintenta la sincronización periódicamente, sin intervención del usuario.
P91: En el backend, ASP.NET Core procesa cada solicitud de forma asíncrona, permitiendo atender múltiples solicitudes concurrentes de distintos técnicos sin bloquear el servidor.
P92: La confirmación final ocurre solo cuando PostgreSQL confirma el commit de la transacción, incluyendo la política de Row-Level Security (RLS) aplicable al usuario que originó la solicitud.

P148: Procesos
P149: La app detecta ausencia de conexión y escribe el registro en SQLite local (proceso offline).
P150: 3
P151: Desarrollo
P152: Al reconectar, el Background Service invoca el caso de uso RegistrarIntervencion (capa Application), que delega el cálculo a la entidad Intervencion (capa Domain).
P153: 4
P154: Lógica
P155: Intervencion.CalcularBalanceMasa() y CalcularEstadoSemaforo() determinan que el resultado es "rojo" (balance de masa > 15%).
P156: 5
P157: Desarrollo
P158: AFRISAN.Infrastructure persiste el registro mediante Entity Framework Core, dentro de una transacción.
P159: 6
P160: Física
P161: La transacción se ejecuta en Azure App Service y se confirma en PostgreSQL 16 (Supabase Cloud), aplicando la política RLS del rol Técnico.
P162: 7
P163: Física
P164: Power BI Service consulta la base de datos y refleja la nueva intervención crítica en el dashboard ejecutivo y en el ranking de locales críticos.
P165: 8
P166: Procesos
P167: El Jefe de grupo ve la alerta en el semáforo GEI en tiempo real (CU-03) desde la app web (Blazor), sin haber recargado manualmente la página.
P168: Este escenario demuestra que ninguna de las cinco vistas es suficiente por sí sola para entender el sistema: la Vista Lógica explica qué se calcula, la de Desarrollo dónde vive ese cálculo en el código, la de Procesos cómo se comporta con o sin conexión, la Física dónde se ejecuta cada parte, y el escenario conecta todo con el caso de uso real que le importa a AFRISAN.
