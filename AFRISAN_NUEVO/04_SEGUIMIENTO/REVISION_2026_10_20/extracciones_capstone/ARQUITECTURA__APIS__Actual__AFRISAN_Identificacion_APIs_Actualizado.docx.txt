P20: 1. Introducción
P21: El presente documento identifica y describe preliminarmente las APIs REST necesarias para soportar las principales funcionalidades del sistema AFRISAN.
P22: La definición se encuentra alineada con la arquitectura cliente-servidor de tres capas seleccionada para el proyecto:
P23: Capa de presentación: Afrisan.Web, desarrollada con Blazor WebAssembly.
P24: Capa de lógica de negocio: Afrisan.Api, desarrollada con ASP.NET Core Web API.
P25: Capa de persistencia: PostgreSQL mediante Supabase.
P26: La API constituye el punto central de comunicación entre la interfaz de usuario y la base de datos, permitiendo mantener las reglas de negocio fuera de la capa de presentación y centralizar las validaciones relacionadas con cilindros, gases refrigerantes, movimientos e historial.
P27: Este documento diferencia entre los endpoints que forman parte del desarrollo actual de AFRISAN y aquellos que corresponden al diseño objetivo o funcionalidades previstas para etapas posteriores.
P28: Los contratos definitivos, mecanismos de autenticación, validaciones exhaustivas y aspectos de seguridad serán refinados durante la etapa de desarrollo.
P29: 2. Convenciones generales
P30: 2.1 Formato de intercambio
P31: La comunicación entre la aplicación cliente y la API utiliza principalmente JSON (application/json) para el intercambio de información en solicitudes y respuestas HTTP.
P32: 2.2 Arquitectura de comunicación
P33: La comunicación principal de AFRISAN corresponde al siguiente flujo:
P34: Afrisan.Web  →  Afrisan.Api  →  PostgreSQL / Supabase
P35: La interfaz web realiza solicitudes HTTP a la API. La API procesa las reglas de negocio y utiliza Entity Framework Core y Npgsql para acceder a PostgreSQL. La capa de presentación no debe acceder directamente a la base de datos.
P36: 2.3 Versionado de API
P37: Actualmente, el desarrollo utiliza rutas con el prefijo /api/.... Para futuras versiones se propone incorporar versionado mediante /api/v1/.... Esto permitirá modificar la API en el futuro sin afectar directamente a clientes que dependan de versiones anteriores.
P38: Por lo tanto, el uso de /api/v1 descrito en las funcionalidades futuras representa el diseño objetivo de la API y no necesariamente el estado actual de todos los endpoints implementados.
P39: 2.4 Autenticación y autorización
P40: Se contempla incorporar autenticación mediante JSON Web Token (JWT). El token deberá ser enviado en el encabezado:
P41: Authorization: Bearer <token>
P42: La autenticación y el sistema completo de roles corresponden a funcionalidades que deberán implementarse y verificarse durante el desarrollo. No se considera que todos los endpoints actuales dispongan todavía de este mecanismo.
P43: 2.5 Transporte
P44: Para un ambiente productivo se contempla el uso obligatorio de HTTPS/TLS con el objetivo de proteger las comunicaciones entre los clientes y la API. Durante las etapas de desarrollo pueden utilizarse conexiones HTTP dentro del entorno local controlado.
P45: 2.6 Formato de fechas
P46: Las fechas deberán utilizar preferentemente el estándar ISO 8601. Ejemplo:
P47: 2026-09-25T14:32:00-03:00

P285: almacenamiento local;
P286: identificación de registros;
P287: idempotencia;

P289: control de versiones;

P304: 5. Especificación preliminar de endpoints críticos
P305: 5.1 POST /api/v1/auth/login
P306: Estado: Propuesto / pendiente de implementación.
P307: Su objetivo será autenticar al usuario y devolver un token de sesión junto con su información de autorización.
P308: Solicitud propuesta
P309: {  "usuario": "ipereza",  "password": "********"}
P310: Respuesta propuesta
P311: {  "token": "token_jwt",  "usuario": {    "id_usuario": "u-0231",    "nombre": "Ignacio Pérez",    "rol": "tecnico",    "zona_bodega": "Zona Sur"  }}
P312: 5.2 Registro de intervención
P313: POST /api/v1/intervenciones
P314: Estado: Funcionalidad futura.
P315: Permitirá registrar una intervención asociada a una orden de trabajo.
P316: Solicitud preliminar
P317: {  "n_ot": "OT-48213",  "id_local": "loc-014",  "id_cilindro": "cil-0231",  "id_autoriza": "u-0087",  "tipo_intervencion": "correctivo",  "peso_retirado": 18.0,  "peso_utilizado": 14.8}
P318: Los campos definitivos deberán validarse durante el desarrollo de las historias de usuario relacionadas con pesaje, órdenes de trabajo y conciliación.
P319: 5.3 Despacho de cilindro
P320: Actualmente AFRISAN dispone de una operación de despacho equivalente a:
P321: POST /api/MovimientosInventario/despacho/{cilindroId}
P322: Esta operación permite registrar el despacho de un cilindro y modificar su estado. En la API versionada futura podrá evolucionar hacia:
P323: POST /api/v1/movimientos/despacho/{cilindroId}
P324: Deberá verificarse que la operación:
P325: no permita despachar un cilindro no disponible;
P326: mantenga coherencia entre estado y movimientos;
P327: registre la información necesaria para trazabilidad;
P328: controle operaciones simultáneas sobre el mismo cilindro.
P329: 5.4 Retorno de cilindro
P330: Actualmente AFRISAN dispone de:
P331: POST /api/MovimientosInventario/retorno/{cilindroId}
P332: Su objetivo es registrar la devolución de un cilindro anteriormente despachado. Durante el desarrollo posterior se contempla incorporar información adicional de pesaje y conciliación.
P333: 5.5 Historial de movimientos
P334: Actualmente se utiliza:
P335: GET /api/MovimientosInventario/historial/{cilindroId}
P336: Permite recuperar los movimientos asociados a un cilindro. Este servicio es relevante para la trazabilidad del sistema y para la consulta mediante identificación QR. La incorporación futura de usuarios permitirá registrar también el actor responsable de cada operación.
P337: 5.6 Sincronización offline
P338: Endpoint objetivo:
P339: POST /api/v1/sync
P340: Estado: No implementado.
P341: La funcionalidad se considera parte de una etapa futura de AFRISAN. Una posible solicitud sería:
P342: {  "dispositivo_id": "movil-01",  "registros": [    {      "tipo": "movimiento_inventario",      "payload": {},      "creado_en": "2026-09-25T11:40:00"    }  ]}
P343: Antes de su implementación deberá definirse una estrategia formal para resolver conflictos. No se establece todavía una política definitiva de “última escritura gana”, ya que dicha decisión requiere ser analizada y validada.

P385: 7. Seguridad y control de acceso propuesto
P386: La seguridad deberá aplicarse principalmente desde la capa de lógica de negocio y no depender únicamente de la interfaz. Para las siguientes etapas se propone:
P387: implementar autenticación mediante JWT;
P388: definir roles y permisos;
P389: validar autorización antes de operaciones restringidas;
P390: almacenar contraseñas mediante algoritmos de hash adecuados;
P391: impedir que contraseñas o tokens sean escritos en logs;
P392: utilizar HTTPS en ambientes productivos;
P393: validar los datos recibidos por la API;
P394: incorporar rate limiting en endpoints sensibles;
P395: registrar operaciones relevantes mediante mecanismos de auditoría;
P396: mantener secretos y credenciales fuera del código fuente;
P397: restringir el acceso a los recursos según usuario y rol.
P398: La incorporación de estos mecanismos deberá realizarse progresivamente durante la Fase 2.
P399: 8. Relación con la arquitectura de tres capas
P400: La API constituye la capa de lógica de negocio de AFRISAN. Su función es evitar que la interfaz de usuario acceda directamente a PostgreSQL y centralizar las reglas que deben mantenerse independientemente del dispositivo utilizado.
P401: La arquitectura queda estructurada como:
P402: Afrisan.WebBlazor WebAssembly        ↓     JSON        ↓Afrisan.ApiASP.NET Core Web API        ↓Entity Framework Core / Npgsql        ↓PostgreSQL / Supabase
P403: Las futuras aplicaciones móviles deberán utilizar igualmente la API para acceder a la información central. Esto permite mantener las mismas reglas de negocio para diferentes interfaces.

P428: 10. Conclusión
P429: La identificación de APIs define el contrato de comunicación entre la capa de presentación, la lógica de negocio y la persistencia de AFRISAN.
P430: La arquitectura actual permite continuar desarrollando funcionalidades sin acoplar directamente la interfaz con la base de datos.
P431: Durante la Fase 1 se establece el diseño general y se identifican los principales servicios necesarios. Durante la Fase 2, los endpoints deberán evolucionar conforme se implementen las historias de usuario, se incorporen pruebas, seguridad, trazabilidad y nuevas reglas de negocio.
P432: La especificación presentada en este documento debe entenderse como una base técnica evolutiva, en la cual se distingue claramente entre los servicios actualmente implementados y las capacidades previstas para etapas posteriores del proyecto.
