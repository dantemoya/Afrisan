P19: 1. Introducción
P20: Este documento identifica y especifica preliminarmente los endpoints REST necesarios para soportar los requisitos funcionales del ERS del proyecto APT AFRISAN. El diseño detallado de contratos (esquemas completos de solicitud/respuesta, validaciones exhaustivas) se refinará durante la etapa de desarrollo, en conjunto con el resto del equipo.
P21: 2. Convenciones generales
P22: Formato de intercambio de datos: JSON (application/json) en el cuerpo de solicitudes y respuestas.
P23: Autenticación: JSON Web Token (JWT), enviado en el encabezado Authorization: Bearer <token>, salvo en /api/v1/auth/login.
P24: Versionado: todas las rutas se prefijan con /api/v1, para permitir futuras versiones de la API sin romper la compatibilidad con clientes existentes.
P25: Transporte: todas las comunicaciones se realizan exclusivamente sobre HTTPS/TLS (RNF-02 del ERS).
P26: Formato de fechas: ISO 8601 (por ejemplo, 2026-08-26T14:32:00-04:00).

P183: Recibe un lote de registros generados en modo offline por la app móvil y los concilia con la base de datos central.

P185: {
P186:   "dispositivo_id": "movil-ipereza-01",
P187:   "registros": [
P188:     { "tipo": "intervencion", "payload": { "...": "..." }, "creado_en": "2026-08-26T11:02:00" },
P189:     { "tipo": "movimiento_inventario", "payload": { "...": "..." }, "creado_en": "2026-08-26T11:40:00" }
P190:   ]
P191: }
P192: Respuesta (200 OK)
P193: {
P194:   "sincronizados": 2,
P195:   "conflictos": 0,
P196:   "detalle": []
P197: }
P198: En caso de conflicto (por ejemplo, un cilindro que ya fue movido por otro usuario), el registro correspondiente se reporta en el arreglo "detalle" con el motivo del conflicto, conforme a la regla de resolución definida (última escritura gana, con marca de tiempo), según el riesgo R4 identificado en el ERS.

P215: 5. Manejo de errores
P216: La API utiliza códigos de estado HTTP estándar para señalar el resultado de cada solicitud:
P217: Código
P218: Nombre
P219: Uso
P220: 200
P221: OK
P222: Solicitud procesada correctamente.
P223: 201
P224: Created
P225: Recurso creado correctamente (por ejemplo, una nueva intervención).
P226: 400
P227: Bad Request
P228: La solicitud no cumple el formato o las validaciones esperadas.
P229: 401
P230: Unauthorized
P231: El token de autenticación no fue enviado o no es válido.
P232: 403
P233: Forbidden
P234: El usuario autenticado no tiene permisos para el recurso solicitado (rol insuficiente).
P235: 404
P236: Not Found
P237: El recurso solicitado no existe.
P238: 409
P239: Conflict
P240: Conflicto de sincronización o de datos (por ejemplo, un registro duplicado desde offline).
P241: 422
P242: Unprocessable Entity
P243: La solicitud tiene formato válido pero incumple una regla de negocio.
P244: 500
P245: Internal Server Error
P246: Error no controlado en el servidor.
P247: 6. Seguridad y control de acceso
P248: Cada endpoint valida el rol del usuario autenticado antes de ejecutar la operación solicitada, conforme a la columna "Roles con acceso" del catálogo (sección 3).
P249: Las contraseñas se almacenan cifradas (hash) y nunca se transmiten ni se registran en texto plano en los logs del servidor.
P250: Se recomienda aplicar límites de tasa de solicitudes (rate limiting) sobre /api/v1/auth/login para mitigar ataques de fuerza bruta.
P251: Se recomienda validar y sanitizar todas las entradas del usuario en el backend, para mitigar inyección SQL (SQLi) y Cross-Site Scripting (XSS), conforme al requisito RNF-01 del ERS.
P252: El endpoint /api/v1/intervenciones/{id} (PUT), utilizado para corregir registros, escribe automáticamente una entrada en la tabla auditoria (valores_anteriores, valores_nuevos, usuario y fecha), consultable mediante GET /api/v1/auditoria, conforme al panel de corrección descrito en el ERS.
